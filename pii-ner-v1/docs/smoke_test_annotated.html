Cell 0 — Markdown

Success Criteria

Success criteria: - Eval loss < 10 - F1 on training data > 0.90 - Runs in under 10 minutes on a T4 GPU
Why these numbers?
• Eval loss < 10 — CRF loss is a negative log-likelihood over the entire sequence, not per-token cross-entropy. A loss of 0.8 means ~45% probability on the correct tag sequence out of 89seq_len paths. Values under 10 mean the model is confidently predicting the right sequences.

• F1 > 0.90 — Since we're evaluating on the same 100 training examples, this is an overfit test. If the model can't memorize 100 examples, the wiring is broken. 0.90 (not 1.0) accounts for rare entity types that may only appear once in 100 examples.

• Under 10 minutes — Practical constraint. A T4 has 16GB VRAM. If the model can't train in 10 min on 100 examples, something is wrong with batch sizes or memory.

Model Assembly: The Constructor

When you call PiiNerModel(config), four components are built:

Key asymmetry: DeBERTa is pretrained (already understands language). Everything else is randomly initialized (knows nothing about PII). This is why differential learning rates are essential.

Component 1: DeBERTa v3-xsmall

self.deberta = DebertaV2Model.from_pretrained(config.backbone) context_dim = self.deberta.config.hidden_size # 384

What Is DeBERTa?

A transformer encoder from Microsoft. "v3-xsmall" is the smallest variant:

Parameters70.7M
Hidden size384
Layers12
Attention heads6
Vocabulary128K tokens (SentencePiece)

What from_pretrained Does

Downloads weights pretrained on English text (books, Wikipedia, web). These weights already encode:

  • Word meaning and syntax
  • Context-dependent representations
  • "John" in "Dear John," vs "John Smith"
context_dim = 384 is critical. It's the size of the vector DeBERTa produces for each token. Every downstream component must accept or project to this dimension. The CharCNN outputs 150-dim, so the GatingFusion projects it up to 384.

Component 2: CharCNN Encoder

self.char_cnn = CharCNNEncoder( vocab_size=256, # ASCII byte range embed_dim=50, # Each character → 50-dim vector filter_widths=[3, 4, 5], # 3-gram, 4-gram, 5-gram convolutions num_filters=[50, 50, 50], # 50 filters per width dropout=0.1, )
Why a character-level CNN at all? DeBERTa works on subword tokens. It sees "555-12-3456" as something like ["_555", "-12", "-34", "56"]. It can't directly "see" the XXX-XX-XXXX pattern of an SSN. The CharCNN looks at the raw characters of each token and can learn patterns like digit sequences, @ symbols, dashes in specific positions — exactly the surface features that distinguish structured PII.

CharCNN: Step by Step

What happens inside CharCNNEncoder.forward()

Step 1: Embed characters
char_ids (batch, seq_len, 20) → nn.Embedding(256, 50) → (batch × seq_len, 20, 50)
Each of the 20 character slots becomes a 50-dimensional vector. Padding (0) maps to a zero vector.
↓
Step 2: Transpose for Conv1D
(batch × seq_len, 50, 20)
Conv1D expects (batch, channels, length). Channels = embed_dim, length = max_char_len.
↓
Step 3: Three parallel convolutions + ReLU + max-pool
• Conv1d(50, 50, kernel_size=3) → ReLU → max over time → 50-dim (trigrams: "555", "@gm")
• Conv1d(50, 50, kernel_size=4) → ReLU → max over time → 50-dim (4-grams: "5-12", "mail")
• Conv1d(50, 50, kernel_size=5) → ReLU → max over time → 50-dim (5-grams: "55-12", "@gmai")
↓
Step 4: Concatenate
[50 + 50 + 50] = 150-dim per token → reshape to (batch, seq_len, 150)
Max-pool over time is the key operation. It picks the strongest activation from each filter across all character positions. Think of it as: "the best match for this character pattern, wherever it occurs in the token."

CharCNN Parameters Explained

vocab_size = 256
The embedding table has 256 rows — one per possible byte value. Characters are converted to their ASCII/UTF-8 byte values. Index 0 is reserved for padding. This means it can handle any character in the Basic Latin range without a separate tokenizer.
embed_dim = 50
Each character is represented as a 50-dimensional vector. This is a learned embedding, not one-hot. The model learns that 'a' and 'A' might be similar, or that digits cluster together. 50 is a standard choice — big enough to capture character relationships, small enough to be fast.
filter_widths = [3, 4, 5]
Three separate Conv1D layers with kernel sizes 3, 4, and 5. A width-3 filter slides over 3 characters at a time (trigrams), width-4 over 4 (4-grams), etc. Together they capture patterns at multiple scales: "555" (3), "@gma" (4), "XX-XX" (5).
num_filters = [50, 50, 50]
50 filters per width = 50 different pattern detectors at each scale. Each filter learns to detect one specific character pattern. 50 × 3 = 150 total features per token. Think of each filter as asking: "does this token contain pattern X?"
max_char_len = 20
Tokens longer than 20 characters are truncated; shorter ones are zero-padded. 20 covers most tokens (average English word is 5 chars, but emails/URLs can be longer). The padding_idx=0 on the embedding ensures padding doesn't contribute signal.

Component 3: Gating Fusion

self.fusion = GatingFusion( char_dim=150, # CharCNN output: 50 + 50 + 50 context_dim=384, # DeBERTa hidden size dropout=0.1, )

The fusion layer blends character features and contextual features with a learned gate:

Step 1: Project char features up: 150-dim → nn.Linear(150, 384) + ReLU → 384-dim
↓
Step 2: Concatenate: [384 char_proj, 384 context] = 768-dim
↓
Step 3: Compute gate: g = sigmoid(Linear(768 → 384)) — values in [0, 1] per dimension
↓
Step 4: Fuse: output = g × char_proj + (1 − g) × context
Why a gate instead of just concatenating? Not all tokens benefit equally from character features. For "John" (a name), contextual meaning matters more → gate goes low. For "555-12-3456" (an SSN), the character pattern is the signal → gate goes high. The model learns this tradeoff per-token, per-dimension.

Gating Fusion: Intuition

The gate learns which signal to trust for each token

High Gate (g → 1): Trust Characters

TokenWhy Characters Win
555-12-3456XXX-XX-XXXX pattern = SSN
user@mail.com@ symbol + .TLD = email
4111-1111-111116 digits = credit card
192.168.1.1Dotted quad = IP address

These are structured PII — you can tell what they are just by looking at the characters.

Low Gate (g → 0): Trust Context

TokenWhy Context Wins
John"Dear John" vs "John St"
Paris"born in Paris" vs "Paris Hilton"
May"in May 2024" vs "May Johnson"
male"gender: male" vs "male connector"

These are contextual PII — the surrounding words determine if it's an entity.

Component 4: CRF Head

self.crf_head = CRFHead( hidden_dim=384, # Must match DeBERTa / fusion output num_labels=89, # BIO tag count dropout=0.1, )

Inside the CRF head, two sub-components:

self.classifier = nn.Linear(384, 89)
Projects each token's 384-dim fused representation to 89 "emission scores" — one per possible BIO tag. These are unnormalized logits: how much each token "looks like" each tag, independently.
↓
self.crf = TorchCRF(89, batch_first=True)
A Conditional Random Field layer with an 89 × 89 transition matrix. This matrix learns: "given that the previous token was tagged X, how likely is it that the current token is tagged Y?" This enforces legal BIO sequences.
The transition matrix is the heart of the CRF. It has 89 × 89 = 7,921 learnable parameters. Each cell [i][j] represents the score for transitioning from tag i to tag j. After training, transitions[B-PERSON][I-PERSON] will be high, but transitions[B-PERSON][I-EMAIL] will be strongly negative.

CRF: Training vs Inference

Training: Compute Loss

clamped_labels = labels.clamp(min=0) log_lik = self.crf( emissions, clamped_labels, mask=mask, reduction="mean" ) loss = -log_lik

clamp(min=0): HF uses -100 for "ignore this token" (special tokens, padding). CRF can't handle negative tag IDs, so we clamp to 0. The mask ensures these positions don't affect the loss.

Negative log-likelihood: The CRF returns log P(correct sequence). We negate it because we want to minimize loss = maximize probability of correct sequence.

Inference: Viterbi Decode

tag_sequences = self.crf.decode( emissions, mask=mask ) # Returns list of lists (variable length) # Pad to seq_len for batching predictions = torch.full( (batch, seq_len), 0, ... ) for i, tags in enumerate(tag_sequences): predictions[i, :len(tags)] = tags

Viterbi algorithm: Finds the single highest-scoring tag sequence globally, not just the best tag per position. This is why CRF output is always a valid BIO sequence — it can't produce I-EMAIL after B-PERSON.

Why pad with 0? Tag ID 0 = "O" (not an entity). crf.decode() returns variable-length lists (only non-masked positions), so we fill a full-size tensor with 0 ("O") and overwrite the real positions. Safe default.

The Complete Forward Pass

What happens when the model processes a batch

1. DeBERTa encodes tokens
input_ids (batch, seq_len) → DeBERTa → context_features (batch, seq_len, 384)
↓
2. CharCNN encodes characters
char_ids (batch, seq_len, 20) → CharCNN → char_features (batch, seq_len, 150)
↓
3. Gating fusion blends both
char (150) + context (384) → GatingFusion → fused (batch, seq_len, 384)
↓
4. Cast to FP32 + disable autocast
fused = fused.float()
CRF's log-sum-exp computation is numerically unstable in FP16. This line forces full precision for the CRF head only, while the rest of the model runs in FP16 for speed.
↓
5. CRF head: emit + decode
fused (batch, seq_len, 384) → Linear → emissions (batch, seq_len, 89) → CRF → predictions (batch, seq_len)

What happens inside load_single_dataset:

2. Takes only the first 100
3. For each example: normalizes raw labels (e.g., "FIRSTNAME" → "B-PERSON") using a label map
4. Tokenizes words into DeBERTa subword tokens and aligns BIO labels

Subword Alignment: The Tricky Part

DeBERTa splits words into subword tokens. Labels must follow.

Example

Original WordLabel
JohnB-PERSON
SmithI-PERSON

But DeBERTa might tokenize "Smith" as two subwords:

Subword TokenAligned Label
[CLS]-100 (ignore)
_JohnB-PERSON
_SmI-PERSON
ithI-PERSON
[SEP]-100 (ignore)

The Rule

  • First subword of a word gets the original BIO tag
  • Continuation subwords get the I- version (B-X becomes I-X)
  • Special tokens ([CLS], [SEP], padding) get -100

-100 is PyTorch's convention for "ignore this position in loss computation." The CRF head clamps these to 0 and masks them out.

char_ids are generated from the original word, not the subword. So both _Sm and ith get the char_ids for "Smith".

Data Collator: Batching the 3D Tensor

collator = PiiDataCollator(tokenizer=tokenizer, max_char_len=20)
Why a custom collator? HuggingFace's default DataCollatorForTokenClassification handles padding for 1D tensors (input_ids, labels) and 2D (attention_mask). But char_ids is 3D: (seq_len, 20) per example. The custom collator:
1. Pops char_ids out of each example before passing to the parent collator
↓
2. Parent pads input_ids, attention_mask, labels to the longest sequence in the batch
↓
3. Manually pads each char_ids with [0] * 20 rows to match the padded sequence length
↓
4. Stacks into (batch_size, padded_seq_len, 20) and adds to the batch dict

Cell 9 — Code (Part 2)

Differential Learning Rates

LR_BACKBONE = 2e-5 LR_HEAD = 1e-3 backbone_params = [p for n, p in model.named_parameters() if "deberta" in n] head_params = [p for n, p in model.named_parameters() if "deberta" not in n] optimizer = AdamW([ {"params": backbone_params, "lr": LR_BACKBONE}, # 2e-5 {"params": head_params, "lr": LR_HEAD}, # 1e-3 ], weight_decay=0.01)

How Parameters Are Split

The split is based on the parameter name:

Name contains "deberta"?GroupLR
Yesbackbone_params2e-5
Nohead_params1e-3

head_params includes: CharCNN (embedding, convolutions), GatingFusion (projection, gate), CRF head (linear classifier, transition matrix). All randomly initialized.

Why 50x Ratio?

Backbone (2e-5): Already has useful language representations. Large updates destroy them. This is a standard fine-tuning LR for DeBERTa.

Head (1e-3): Random weights that need to learn 89 × 89 transition probabilities + character patterns from scratch. Needs to move fast to escape the "predict all O" local minimum.

1e-3 / 2e-5 = 50x. The head learns 50 times faster than the backbone.

PiiTrainer: Custom Training Loop

trainer = PiiTrainer( model=model, args=training_args, train_dataset=dataset, eval_dataset=dataset, # Same data — intentional overfit data_collator=collator, compute_metrics=compute_metrics, optimizers=(optimizer, None), # (optimizer, scheduler) )
eval_dataset=dataset — We're evaluating on the same 100 examples we're training on. This is intentional: the smoke test asks "can the model memorize this data?" If it can't overfit 100 examples, the architecture is broken.
optimizers=(optimizer, None) — The first element is our custom AdamW with differential LRs. The second (None) means "use HF's default learning rate scheduler" (linear decay with warmup). If we passed a custom scheduler, it would override the warmup_ratio from TrainingArguments.
Why PiiTrainer instead of plain Trainer? Two custom methods:
• compute_loss(): Extracts outputs.loss from our PiiNerOutput dataclass (HF Trainer expects a specific output format)
• prediction_step(): Returns outputs.predictions (CRF-decoded tag IDs) instead of raw logits. Without this, compute_metrics would get emission scores instead of actual tag predictions.
Cell 11 — Code

Evaluation & Pass/Fail Logic

eval_results = trainer.evaluate() eval_loss = eval_results.get("eval_loss", float("inf")) loss_ok = eval_loss < 10 f1_ok = eval_results.get('eval_overall_f1', 0) > 0.90 if loss_ok and f1_ok: print("SMOKE TEST PASSED") else: print("SMOKE TEST FAILED")

Why eval_loss not training_loss?

HF Trainer's train_result.training_loss is the average across all steps from epoch 1 to 50. Early epochs have loss >500, so the average can be 126 even when the final epoch's loss is 2.

eval_loss runs a fresh forward pass on the data right now, reflecting the model's current state. Much more meaningful.

What compute_metrics Returns

Uses seqeval for entity-level metrics:

overall_f1Harmonic mean of P and R
overall_precision% of predicted entities that are correct
overall_recall% of real entities that were found
tier_N_recallAverage recall per severity tier
type_X_f1Per-entity-type F1

Entity-level = exact boundary match. Predicting "John" when the gold is "John Smith" scores 0.

Tier Recalls: Why They Matter

Not all PII is equally sensitive

TierTypesTarget RecallRationale
Tier 1 SSN, Credit Card, Bank Account, Passport, Driver's License, Tax ID ≥ 0.98 Direct financial/identity theft risk. Missing one = data breach.
Tier 2 Person, Email, Phone, DOB, Street Address, IP Address ≥ 0.95 High sensitivity. Can identify individuals when combined.
Tier 3 Username, Date, Location, Organization, URL, Age, Gender, ... ≥ 0.90 Moderate sensitivity. Contextual identifiers.
Tier 4 Medical Record, Employee ID, Password, IBAN, Salary, ... ≥ 0.85 Domain-specific. May not appear in all datasets.
In the smoke test, the tier recalls confirm the model isn't just getting easy types right. Our final run achieved 1.000 recall on all 4 tiers — expected for 100 memorized examples.
