1. The Backbone (DeBERTa)
Why DeBERTa and not regular BERT or RoBERTa?

DeBERTa v3 uses two tricks that matter for NER specifically. First, it has "disentangled attention" — it keeps track of what a token means and where it is in the sentence as two separate signals, then combines them. For NER, position matters a lot. "John" at the start of a sentence after "Dear" is probably a name. "John" after "St." is probably a street. DeBERTa is better at using that positional information than BERT.

Second, DeBERTa v3 uses a more efficient pretraining method (replaced token detection instead of masked language modeling), so smaller DeBERTa models punch above their weight compared to equivalently-sized BERT models.

Concrete numbers: On CoNLL-2003 NER, DeBERTa v3-base gets ~93.5 F1 vs BERT-base at ~92.4 F1. That's a full point, which is a lot at that level. The xsmall variant we use is smaller than BERT-base but still competitive because of the better pretraining.
Why xsmall (70M params) instead of base (86M) or large (304M)?

Two reasons: inference speed and deployment cost. This model is meant to run in production scanning documents for PII. A larger model would be more accurate, but the cost scales roughly linearly with parameter count for inference. xsmall is about 4x faster than large at inference time.

The bet is that the CharCNN + CRF architecture compensates for some of the backbone's smaller size. The CharCNN catches structured patterns (SSN formats, email syntax) that even a large transformer struggles with, and the CRF enforces valid sequences that a bigger softmax head wouldn't.

What we're giving up: Probably 1-2 F1 points on contextual entities like names and locations. DeBERTa-base has a 768-dim hidden size vs our 384, so it builds richer contextual representations. If recall on Tier 2 entities (PERSON, EMAIL) is underperforming in full training, upgrading to base is the single highest-impact change to try.
Worth trying: Run the same smoke test with microsoft/deberta-v3-base. If F1 jumps noticeably on 100 examples, it's a sign xsmall is the bottleneck. If it's roughly the same, the head is doing its job and xsmall is fine.
Is 384 hidden dimensions enough to represent 163 different tags?

Yes, and it's not even close to the limit. Think of it this way: the final linear layer is nn.Linear(384, 163). Each of the 163 tags gets a 384-dimensional "template" vector (one row of the weight matrix). The model asks: "which template does this token's representation look most like?" 384 dimensions is plenty of room for 163 templates to be distinct from each other.

The actual bottleneck isn't the final projection — it's whether the 384-dim representations from DeBERTa are rich enough to distinguish ambiguous entities. Can a 384-dim vector capture the difference between "May" the month and "May" the name? Probably yes, because the transformer encodes the surrounding context. But a 768-dim vector would capture it with more headroom.

Should we freeze the backbone for the first few epochs?

We considered this. The idea is: train only the head for a few epochs so the CRF learns basic transition patterns, then unfreeze the backbone and fine-tune everything together. It's a valid strategy, but the warmup + differential LR approach achieves the same effect more smoothly.

With warmup_ratio=0.1, the backbone LR starts near zero and ramps up over the first 10% of training. So in practice, the backbone is nearly frozen for the first ~125 steps. The difference is that it's a gradual transition rather than a hard switch, which tends to train more stably.

When freezing makes more sense: If you were using a much larger backbone (DeBERTa-large, 304M params) with very limited data. Freezing prevents the massive backbone from memorizing the small dataset before the head has learned anything useful. With 360K training examples, this isn't a concern for us.
2. The Character CNN
DeBERTa already uses subword tokenization. Why do we need a character CNN on top?

Because subword tokenization actively destroys the patterns that identify structured PII.

Take an SSN: 555-12-3456. A human sees "three digits, dash, two digits, dash, four digits" and immediately thinks SSN. But DeBERTa's SentencePiece tokenizer might split this into ["_555", "-12", "-34", "56"]. Now the model sees four unrelated subword tokens. It can still learn that this sequence of tokens tends to be an SSN, but it has to learn that pattern from training data rather than recognizing the structural pattern directly.

The CharCNN looks at the raw characters of each token. It can learn a filter that activates on "digit-digit-digit-dash" regardless of how the tokenizer split things up. This is especially valuable for PII types with rigid formats: SSNs, credit cards, IBANs, IP addresses, phone numbers.

How much does it help? In ablation studies on NER tasks, adding a character CNN to a transformer typically adds 0.3-0.8 F1 on standard benchmarks like CoNLL. But for PII-specific tasks with structured entities, the gain is likely larger because the structured patterns are exactly what CharCNN excels at. The only way to know for sure is to run an ablation: train once with CharCNN, once without, compare.
Why filter widths [3, 4, 5]? Would more widths help?

The widths [3, 4, 5] are the "classic" choice from Kim (2014) and Ma & Hsieh (2016). They capture character n-grams of 3, 4, and 5 characters. This covers most of the patterns you'd care about:

WidthWhat It CatchesExamples
3Short patterns, digit runs555, @gm, ://
4Medium patternsmail, .com, -12-
5Longer structural patterns@gmai, XX-XX, https

Adding a width-2 filter would catch character bigrams (individual letter transitions), which is occasionally useful. Adding width-6 or 7 would catch longer patterns but with diminishing returns since max_char_len is only 20. The max-pooling also means longer patterns can be captured as combinations of shorter ones.

Worth trying: Add a width-2 filter: filter_widths=[2,3,4,5], num_filters=[50,50,50,50]. This adds 50 dimensions to the CharCNN output (200 total instead of 150). Cost is negligible. The width-2 filter might help with patterns like repeating digits or specific character pairs that signal PII boundaries.
Is 50 filters per width enough?

50 per width gives us 150 total features. That's 150 different character patterns the model can detect per token. For a model that's primarily relying on the 384-dim DeBERTa features and only using character features as supplementary signal, 150 is reasonable.

The question is whether 50 filters are enough to cover all the character patterns across 81 entity types. Some entity types share patterns (credit cards, IBANs, and phone numbers all involve digit sequences), so there's reuse. But 50 is toward the lower end of what papers typically use.

Worth trying: Bump to 100 filters per width (300 total). This doubles the CharCNN parameter count (~29K to ~58K), which is trivial relative to the 70M backbone. If structured PII types (Tier 1: SSN, credit cards) improve noticeably, the extra filters were needed.
Is max_char_len=20 enough? Emails and URLs can be long.

20 characters covers most tokens you'll encounter in normal text. The average English word is 5 characters. Even most email addresses, when split into tokens by the tokenizer, produce tokens shorter than 20 characters (e.g., john.doe = 8 chars, @gmail.com = 10 chars).

But there are edge cases. A long URL token might be 40+ characters. A complex password like X7kq!mP2@wL9#nB is 15 characters but close to the limit. Anything past 20 characters is simply truncated — the CharCNN never sees characters 21+.

The tradeoff: max_char_len directly affects memory. The char_ids tensor is (batch, seq_len, max_char_len). Going from 20 to 40 doubles the memory for that tensor. It also means the Conv1D operations run on longer sequences. For 20, the cost is negligible. For 40, still small but not zero.
Worth trying: Bump to 30. Covers 99%+ of tokens in practice, modest memory increase. Only go to 40+ if you find the model is specifically failing on long-token entities.
char_embed_dim=50 — why 50?

50 is the standard value from the Ma & Hsieh (2016) NER paper that popularized CharCNN for NER. It's been widely used since and works well in practice.

Here's the intuition: there are 256 possible byte values, and we're projecting them into a 50-dimensional space. That's a ~5x compression, which forces the model to learn that similar characters (digits, lowercase letters, uppercase letters, punctuation) should cluster together. If you made embed_dim too small (say 10), you wouldn't have enough room for meaningful clusters. Too large (say 200) and you're wasting capacity on a lookup table for 256 items.

50 is a sensible default. Changing it to 30 or 75 is unlikely to make a meaningful difference. This is not the parameter to tune first.

Why byte-level (vocab_size=256) instead of Unicode-aware character encoding?

Simplicity. Every character in every language can be represented as a sequence of bytes. By using raw byte values, we avoid maintaining a separate character vocabulary, handling unknown characters, or worrying about Unicode normalization.

The downside: for non-ASCII text (Chinese, Arabic, accented characters), a single character might take 2-4 bytes in UTF-8. The model would see these as separate "characters," which is less natural than seeing them as single code points.

For English PII, this doesn't matter. SSNs, credit cards, emails, phone numbers, IP addresses — they're all ASCII. Names with accents (like "René") would represent the é as two bytes, but the model can learn that pattern. If you expand to multilingual PII detection, a Unicode-aware character vocabulary (say 8K-16K code points) would be worth investigating.
3. Gating Fusion
Why a learned gate instead of just concatenating char and context features?

Concatenation is the simpler approach: just stick the 150-dim char features and 384-dim context features together to get a 534-dim vector, then let the linear layer sort it out. This works, and many papers do it.

The gate adds something concatenation can't: per-token, per-dimension control over which signal to trust. For the token "555" in "SSN: 555-12-3456", the gate can go high (trust characters). For "John" in "My name is John", the gate can go low (trust context). Concatenation passes both signals equally and hopes the downstream classifier figures it out.

The practical difference is usually small (maybe 0.2-0.5 F1), but it matters more when your entity types span the full range from structured (SSN) to contextual (PERSON). That's exactly our case with 81 entity types.

Worth trying: Replace GatingFusion with simple concatenation + a linear projection as a baseline. If the gate version wins clearly on structured PII types (SSN, credit cards) but is similar on contextual types (PERSON, LOCATION), the gate is doing its job.
Could you use attention-based fusion instead?

Yes. Cross-attention fusion would let each context feature "attend" to the character features and vice versa. This is theoretically more expressive than a gate, which is just a scalar blend.

The tradeoff is complexity and parameter count. The gate is two linear layers (~352K params). A cross-attention fusion with a full attention head would be larger and slower, and for the relatively simple task of "blend two representations" it's probably overkill. The gate is the right level of complexity for this job.

If you wanted to go fancier, a more promising direction than cross-attention would be "biaffine fusion" (commonly used in dependency parsing), which models explicit interactions between char and context dimensions. But start with the gate.

4. The CRF Head
Why CRF instead of a regular softmax classifier?

A softmax classifier predicts each token's tag independently. It looks at token 5, says "B-PERSON" with 80% confidence, moves on to token 6, says "I-EMAIL" with 70% confidence. Nobody checks whether B-PERSON followed by I-EMAIL is legal. It's not — you can't continue an EMAIL entity that was never started.

The CRF predicts the entire sequence jointly. It has a 163×163 transition matrix that scores every possible tag-to-tag transition. During training, it learns that B-PERSON → I-PERSON should have a high transition score and B-PERSON → I-EMAIL should be deeply negative. At inference, the Viterbi algorithm finds the globally best tag sequence, so it literally cannot produce invalid transitions.

How much does it help? On standard NER benchmarks (CoNLL-2003 with 4 entity types), CRF adds about 0.2-0.5 F1 over softmax on top of a transformer. That's a modest but consistent gain. However, we have 81 entity types (163 BIO tags), which means many more ways to produce illegal transitions. The CRF's advantage likely grows with the number of labels because there are more constraint violations for it to prevent. With only 4 types, a transformer can implicitly learn the transition patterns. With 81 types, explicit enforcement helps more.
The transition matrix is 163×163 = 26,569 parameters. Is that a lot? Does it scale badly?

26,569 parameters is tiny. The DeBERTa backbone has 70.7 million. The transition matrix is 0.04% of the model.

The computational cost is a different story. CRF training requires computing the "partition function" — summing over all possible tag sequences. The Viterbi algorithm and forward algorithm both run in O(T × N²) time, where T is sequence length and N is the number of tags. With N=163 and T=256, that's 163² × 256 ≈ 6.8 million operations per example. That's significant but still fast on a GPU.

If you went to, say, 500 tags, the N² cost would start to hurt. At 163 it's fine.

Does the CRF actually learn meaningful transitions, or is it just a constraint layer?

Both. It learns real patterns beyond just "don't follow B-PERSON with I-EMAIL." Some examples of what the transition matrix captures:

FromToLearned ScoreWhy
B-PERSONI-PERSONHighNames are usually multi-token
B-SSNI-SSNHighSSNs span multiple tokens
I-PERSONOMediumNames end eventually
OI-PERSONLowCan't continue a name that wasn't started
B-EMAILI-SSNVery lowIllegal cross-type transition
OOHighMost tokens are not entities

It also learns base rates. The transition from the start-of-sequence to O is very high because most sequences start with non-entity tokens. These priors are baked into the transition matrix and supplement the emission scores from the linear layer.

The CRF loss was in the hundreds early in training but the model was "learning." What was it learning?

Think of CRF training in two phases:

Phase 1 (epochs 1-11): Learning the "grammar" — The transition matrix is learning which tag sequences are legal and which are garbage. It's figuring out that O→O is common, that B-X→I-X is valid, and that random cross-type transitions should be penalized. During this phase, the model predicts all-O because O is the safest tag (85-90% of tokens are O), and the transition matrix hasn't yet learned enough to confidently emit B-tags. Loss drops from 300+ to ~40, but F1 stays at zero.

Phase 2 (epoch 12+): Using the grammar — Once the transition scores for valid patterns (B-PERSON→I-PERSON) are high enough relative to the all-O baseline, the CRF starts emitting entity tags. F1 jumps from 0 to 0.01 at epoch 12, then climbs rapidly because the "grammar" is already learned and the model just needs to refine emission scores.

This is characteristic of CRF training. There's a "phase transition" where metrics go from zero to non-zero suddenly. It looks like nothing is happening, then everything happens at once. With a softmax head you'd see gradual improvement from epoch 1 because individual token predictions can be partially correct. With CRF, seqeval requires exact boundary matches, so it's all-or-nothing.
5. Labels & Tagging Scheme
We use BIO tagging. Would BIOES (also called BILOU) be better?

BIOES adds two more tag prefixes: E (End of entity) and S (Single-token entity). So "John Smith" would be B-PERSON E-PERSON instead of B-PERSON I-PERSON, and standalone "Paris" would be S-LOCATION instead of B-LOCATION.

The argument for BIOES: it encodes entity boundaries more explicitly. The model doesn't have to figure out where an entity ends — the E tag tells it directly. In older BiLSTM-CRF papers, BIOES consistently outperformed BIO by about 0.3-0.8 F1.

The argument against: with 81 entity types, BIOES gives us 1 + (81 × 4) = 325 tags instead of 163. The CRF transition matrix becomes 325×325 = 105,625 parameters (4x larger), and the Viterbi decode is 4x slower. With modern transformers that already capture context well, the BIOES advantage is smaller than it was with BiLSTMs.

Our call: BIO with CRF is a solid middle ground. The CRF already enforces valid boundaries, which is the main thing BIOES provides. Going to BIOES would double label count and slow down training/inference for a gain that's likely under 0.5 F1 with a transformer backbone.
Worth trying if: You see boundary errors in evaluation — the model correctly identifies that an entity exists but gets the start or end token wrong. That's the specific failure mode BIOES helps with. If most errors are entity type confusion (calling a LOCATION a PERSON), BIOES won't help.
81 entity types seems like a lot. Are some too rare to learn well?

Almost certainly yes. In the ai4privacy dataset, entity types follow a long-tail distribution. PERSON, EMAIL, and LOCATION might have tens of thousands of examples each. CRYPTO_WALLET, GENETIC_DATA, and TRADE_UNION might have a few hundred or even fewer.

The model will struggle with rare types. If CRYPTO_WALLET appears only 200 times in 360K examples, the model has very few positive examples to learn from, while seeing millions of non-entity tokens.

What to watch: After full training, check per-type recall. If any Tier 1 or Tier 2 type has recall below target, you need to either: (a) oversample that type during training, (b) add synthetic training data for it, or (c) consider merging very rare types into broader categories.

The 4-tier system is designed with this in mind. Tier 4 has a relaxed target of 0.85 recall because those types are rarer and harder. The tiers focus evaluation attention on the types that matter most.

6. Training Configuration
Why differential learning rates and not layer-wise learning rate decay (LLRD)?

LLRD is a technique where each transformer layer gets a progressively smaller learning rate. Layer 12 (closest to the output) might use 2e-5, layer 11 uses 2e-5 × 0.95, layer 10 uses 2e-5 × 0.95², and so on. The idea is that lower layers learn more general features that shouldn't change much, while upper layers learn more task-specific features that should adapt more.

Our approach is simpler: one LR for everything in DeBERTa (2e-5), one LR for everything in the head (1e-3). Two groups instead of 12+.

The tradeoff: LLRD is more fine-grained and generally gives a small improvement (0.1-0.3 F1 on NER tasks in published results). But it adds a hyperparameter (the decay factor, typically 0.9-0.95) and makes the optimizer setup more complex. For a smoke test and initial training, the 2-group approach is simpler and gets you 95% of the benefit. LLRD is a good thing to try once the basic model is working.
To implement LLRD: Instead of splitting parameters by "deberta" vs not, you'd iterate over model.deberta.encoder.layer and assign each layer a decayed LR. The head still gets 1e-3. A decay factor of 0.95 with base LR 2e-5 means layer 1 gets ~1.2e-5 and layer 12 gets 2e-5. This is a straightforward change to the optimizer setup in the training cell.
Is the 50x ratio between head LR and backbone LR optimal?

50x (1e-3 / 2e-5) is on the higher end of typical ratios. For standard NER with a softmax head, people usually use 5-10x (e.g., backbone 2e-5, head 1e-4 or 2e-4).

We use a higher ratio because the CRF head has more work to do than a simple softmax head. It needs to learn a 163×163 transition matrix from scratch, plus character CNN patterns, plus the gating mechanism. All of these are randomly initialized and need to move fast. At a lower head LR (say 1e-4), the CRF takes many more epochs to escape the "all-O" trap, which we saw in Run 1.

What if 50x is too aggressive? If you see the head overfitting before the backbone has fully adapted (training loss drops to near-zero but validation loss plateaus), the head LR might be too high. For full training on 360K examples, you might want to try head LR of 5e-4 (25x ratio) and see if it generalizes better.
RatioHead LRWhen to Use
10x2e-4Simple softmax head, few labels

Why AdamW? Would a different optimizer help?

AdamW is the de facto standard for transformer fine-tuning. It combines Adam's adaptive learning rates with decoupled weight decay. Virtually all recent NER papers use it.

Other options:

OptimizerVerdictWhy
SGDNot recommendedMuch slower convergence for transformers. You'd need 10x the epochs.
Adam (not W)Slightly worseWeight decay is coupled with gradient, which causes regularization issues. AdamW fixes this.
AdaFactorWorth tryingUses less memory (no second moment estimate). Useful if you upgrade to a larger backbone and memory is tight.
LAMB / LARSNot neededDesigned for very large batch sizes (1000+). Overkill for batch size 16.

Sticking with AdamW is the right call. It's well-understood, well-tested, and compatible with HuggingFace's learning rate schedulers.

Is effective batch size 16 the right choice?

For NER fine-tuning, effective batch sizes of 16-32 are standard. The batch size affects two things:

Gradient noise: Smaller batches have noisier gradients, which can actually help escape local minima (like the all-O trap) but make training less stable. Larger batches have smoother gradients and converge more predictably.

CRF interaction: The CRF loss is computed per-sequence and averaged. With batch size 16, you're averaging over 16 sequences. Sequences with many entities contribute more to the loss than sequences with few entities. If the batch is too small, the gradient is dominated by whichever examples happen to be in that batch.

Our setup: 4 per device × 4 accumulation steps = 16 effective. This is driven by the T4's 16GB VRAM constraint (can't fit more than 4 examples of seq_len 256 with DeBERTa). The accumulation gets us to a reasonable effective batch size without requiring more memory.
For full training: If using a GPU with more memory (A100 with 40/80GB), try per_device_batch_size=8 or 16 with accumulation=2, for effective batch size 16-32. Larger effective batch sizes up to 32 can slightly improve final F1 on NER.
Is warmup_ratio=0.1 right?

0.1 (10% of total training steps) is standard for transformer fine-tuning. The DeBERTa paper uses it. BERT's original paper used a fixed number of warmup steps, but ratio-based is more convenient because it adapts to your dataset size and epoch count.

What warmup does: for the first 10% of steps, the learning rate starts at zero and linearly increases to the target. This prevents destructive updates to the pretrained weights in the first few steps when the randomly initialized head is producing garbage gradients.

When to change it: If you see a loss spike in the first few epochs (loss shoots up, then recovers), warmup might be too short. Try 0.15 or 0.2. If training seems to "waste" early epochs making no progress, warmup might be too long. For most NER tasks, 0.1 is fine.
Is weight_decay=0.01 right? Should backbone and head have different values?

0.01 is the standard value from the BERT and DeBERTa papers. Weight decay acts as L2 regularization, preventing weights from growing too large. It's applied to all parameters except biases and layer norm weights (AdamW and HuggingFace handle this automatically).

In our setup, the same 0.01 applies to both backbone and head parameter groups. This is fine for the backbone but may be slightly too aggressive for the head, which is learning from scratch and needs its weights to grow initially. In practice, the high head LR (1e-3) overwhelms the 0.01 decay, so it doesn't matter much.

An option for full training: Set weight decay to 0 for the head parameter group. This lets the CRF transition matrix and CharCNN filters grow freely without regularization. Whether this helps depends on whether the head overfits — which you'll see in the gap between training and validation loss.

For full training: Use early stopping. Monitor validation F1 every epoch; stop if it doesn't improve for 3 consecutive epochs. You might converge in 6-7 epochs rather than 10. Or you might want 12-15 if the CRF takes longer to settle with the full label distribution.
Does label smoothing work with CRF?

Standard label smoothing (mixing the one-hot target with a uniform distribution) doesn't directly apply to CRF loss. CRF loss is a negative log-likelihood over sequences, not a per-token cross-entropy. You'd need to modify the partition function to account for smoothed targets, which is non-trivial.

That said, the CRF naturally provides a form of "soft" training because the loss considers all possible sequences, not just the argmax. The partition function already distributes probability mass across alternative tag sequences. So CRF training is already less "sharp" than per-token cross-entropy with hard labels.

Bottom line: Don't try to add label smoothing to the CRF loss. If you want a regularization effect, use dropout (we do, at 0.1) or weight decay (we do, at 0.01). These are simpler and well-understood with CRF.
7. Data & Sequence Length
max_seq_len=256 — are we losing PII by truncating?

Yes, potentially. If a document is 400 tokens long and an SSN appears at position 350, we'll never see it because we truncate at 256. This is a real concern for production use.

The tradeoff is memory and speed. DeBERTa's self-attention is O(n²) in sequence length. Doubling from 256 to 512 means 4x the attention computation and 4x the memory for attention matrices. On a T4 with 16GB, you'd need to halve the batch size.

max_seq_lenAttention costBatch size on T4Coverage
1281x8-16Short texts only. Missing a lot.
2564x4Covers most paragraphs and short docs.
51216x1-2Covers most documents. Standard for BERT.
102464xOOM on T4Long documents. Need A100.
The production solution: Use a sliding window at inference time. Split long documents into overlapping 256-token chunks (e.g., stride of 128), run the model on each chunk, and merge predictions. This way you train on 256-token chunks but can handle arbitrarily long documents. The overlap ensures entities at chunk boundaries aren't missed.
For full training: If most of your training data is under 256 tokens, keep it at 256 for speed. If you have a lot of longer documents in the training set, try 384 or 512 with a smaller batch size and more gradient accumulation steps to compensate.
We only used ai4privacy for the smoke test. Should we have used all 3 datasets?

For the smoke test, using one dataset is fine. The smoke test asks "is the model wired correctly?" not "does it generalize across datasets?" If the model can overfit 100 examples from one dataset, the architecture works. Adding more datasets would just slow down the test without changing the answer.

For full training, using all three datasets (ai4privacy, Nemotron-PII, Gretel) is important. Each dataset has different annotation conventions, entity distributions, and text styles. Training on all three forces the model to generalize rather than memorize one dataset's quirks.

Watch out for label conflicts. Different datasets might annotate the same entity differently. ai4privacy might label "New York" as two tokens (B-LOCATION, I-LOCATION) while Gretel labels it as one token (B-LOCATION) because they pre-joined it. The label normalization in label_schema.py handles type mapping (FIRSTNAME → PERSON), but boundary conventions can still differ. Check the per-dataset F1 after full training to catch these issues.
100 examples for the smoke test — is that the right number?

100 is a sweet spot. Here's why:

  • Too few (10-20): Not enough entity diversity. You might not see any examples of SSN or IBAN in 10 examples, so you can't tell if the model handles those types.
  • Too many (1000+): Takes too long to overfit. The whole point of a smoke test is speed. 1000 examples on 50 epochs would take an hour instead of 8 minutes.
  • 100: Gives you at least a few examples of most common entity types, and can be memorized in 50 epochs in under 10 minutes. Good balance.

Even with 100, rare entity types (IBAN, CRYPTO_WALLET) might not appear at all. That's expected. The smoke test validates the architecture, not coverage of every type.

8. Numerical Precision (FP16/FP32)
Why do we need to cast to FP32 for the CRF? What breaks in FP16?

The CRF's forward algorithm computes the "partition function" using log-sum-exp over all possible tag sequences. This involves:

  1. Exponentiating emission scores (which can be large positive or negative numbers)
  2. Summing these exponentials across 163 tag options at each position
  3. Taking the log of the sum
  4. Repeating this for every position in the sequence (up to 256 times)

FP16 has a maximum representable value of ~65,504. After a few iterations of exp → sum → log → add, it's easy to exceed this and get inf. Once any value goes to inf, the gradients become NaN, and training collapses.

FP32's max is ~3.4 × 1038, which is effectively impossible to exceed with log-sum-exp accumulations.

Our solution (two lines):
fused = fused.float() — casts the input tensor to FP32
with torch.amp.autocast(..., enabled=False): — prevents PyTorch's auto-mixed-precision from casting the CRF's linear layer back to FP16

The rest of the model (DeBERTa, CharCNN, GatingFusion) runs happily in FP16. Only the CRF head needs FP32. This gives us the speed benefit of FP16 for the expensive transformer while keeping the CRF stable.
Could we use BF16 instead of FP16+FP32?

BF16 (bfloat16) has the same exponent range as FP32 (max ~3.4 × 1038) but with reduced precision (8 mantissa bits vs 23). This means it won't overflow during log-sum-exp, solving the CRF instability without the FP32 cast.

The catch: BF16 requires Ampere or newer GPUs (A100, A10, RTX 3090+). The T4 (Turing architecture) does not support BF16. Since the smoke test targets T4, we use FP16+FP32 for compatibility.

For full training on A100: Try bf16=True instead of fp16=True and remove the FP32 cast. This is simpler and slightly faster because there's no precision mismatch. Check that eval loss matches the FP16+FP32 baseline to confirm nothing changed.
9. What to Tune First
If I could only change 3 things to improve the model, what should they be?

In priority order:

1. Backbone size: try DeBERTa v3-base (86M, 768-dim)
This is the single biggest lever. Going from 384 to 768 hidden dimensions gives the model much richer contextual representations. It roughly doubles inference cost, but for PII detection where accuracy matters more than speed, it's usually worth it. Expected gain: 1-3 F1 points on contextual entities (PERSON, LOCATION, ORGANIZATION).
2. Layer-wise learning rate decay (LLRD)
Replace the 2-group optimizer with per-layer LRs (decay factor 0.9-0.95). This preserves lower-layer general features while letting upper layers adapt more. Expected gain: 0.3-0.8 F1 points. Low effort to implement, no inference cost.
3. max_seq_len: increase to 384 or 512
More context helps the model resolve ambiguous entities and catches PII that appears later in documents. Expected gain: depends on your data distribution. If most training texts are under 256 tokens, minimal gain. If many are longer, potentially significant.

After these three, the next tier would be: CharCNN filter count (50→100), adding a width-2 filter, and tuning the head-to-backbone LR ratio for full training.

Is there anything fundamentally wrong with this architecture that we should rethink?

No. DeBERTa + CharCNN + CRF is a well-proven architecture for NER. Each component has clear motivation:

  • DeBERTa gives you strong contextual understanding from pretraining
  • CharCNN adds pattern recognition for structured entities that subword tokenization obscures
  • Gating fusion lets the model dynamically choose which signal to trust per token
  • CRF enforces valid BIO sequences, which matters more with 81 entity types than with 4

The one thing to keep an eye on is whether the CharCNN + GatingFusion adds enough value to justify the added complexity. After full training, run an ablation: train the same model but without the CharCNN (set char_ids=None so the forward pass uses context features only). If the CharCNN model wins by 0.5+ F1 on structured PII types, keep it. If the gap is tiny, you could simplify to DeBERTa + CRF and save some complexity.

The architecture is not the bottleneck right now. The smoke test proved it works. The next wins will come from data (more examples, better label quality, oversampling rare types) and training config (LLRD, longer sequences, early stopping) rather than architectural changes.
