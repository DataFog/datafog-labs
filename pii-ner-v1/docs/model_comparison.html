0. The 30-Second Version

SpaCy is fast and cheap but can only find about 7 out of 81 PII types. It needs regex bolted on for everything else. Good baseline, not a real PII solution on its own.

GLiNER 2 is flexible and can find any entity type you describe, without retraining. But it's 9x larger, 5-8x slower, degrades past 30 entity types, and has no character-level features for structured PII like SSNs.

DataFog v1 is purpose-built for PII. Smaller, faster, with character-level pattern detection and CRF sequence constraints. But it's unproven — the smoke test passed, but full training hasn't happened yet.

The core bet: A small model that's designed specifically for PII should beat a large model that's designed for everything. That bet is reasonable, but we haven't proven it yet.
1. What Are These Three Models?
What is SpaCy Large, exactly?

SpaCy's en_core_web_lg is a general-purpose NLP pipeline trained on the OntoNotes 5.0 corpus. It uses a CNN-based architecture (not a transformer) with GloVe word vectors. It's 741 MB, most of which is the word vector table.

For PII work, SpaCy is almost always used through Microsoft Presidio — an open-source framework that combines SpaCy's NER (for names, organizations, locations) with regex rules (for SSNs, credit cards, emails, phone numbers) and validation logic (like Luhn checksums for credit cards).

SpaCy also offers en_core_web_trf, a transformer-based model using RoBERTa-base (125M params). It's significantly more accurate (90% F1 vs 85% F1) but 20-30x slower on CPU. Most Presidio deployments use the CNN model for speed.

Think of SpaCy/Presidio as: A fast rule-based system with an NER model for names and locations bolted on. It's a framework, not a model. Performance depends entirely on how you configure it.
What is GLiNER 2?

GLiNER is a family of zero-shot NER models. "Zero-shot" means you tell it what entity types to look for at inference time — no retraining needed. You pass entity type names (like "PERSON", "SSN", "CREDIT_CARD") as part of the input, and the model matches text spans to those types.

The original GLiNER (NAACL 2024) uses DeBERTa-v3 as the backbone. GLiNER 2 (EMNLP 2025) extends this to multi-task information extraction. Several organizations have fine-tuned GLiNER variants specifically for PII: NVIDIA (nvidia/gliner-PII), Gretel (gretel-gliner-bi-base), and Knowledgator.

The large variant has ~460M parameters. The medium variant uses DeBERTa-v3-base (~90M params). GLiNER2 itself is ~205M params.

Think of GLiNER as: A flexible general-purpose entity extractor that you can point at any entity type. Jack of all trades, master of none — unless you fine-tune it for a specific domain, at which point you lose the zero-shot advantage.
What is DataFog PII-NER v1?

Our model. DeBERTa-v3-xsmall (70.7M params, 384-dim) combined with a Character CNN (catches patterns like XXX-XX-XXXX), a gating fusion layer (dynamically blends character and context signals per token), and a CRF head (enforces valid BIO tag sequences).

It's designed from the ground up for one task: finding PII in English text. Fixed taxonomy of 81 entity types, 4 severity tiers, trained on 360K PII-specific examples. Target: ONNX INT8, ~25 MB, runs on CPU at ~10ms per 128 tokens.

Important caveat: The smoke test passed (F1 0.992 on 100 memorized examples). Full training on 360K examples hasn't happened yet. The performance targets below are projections based on architecture design and literature, not measured results. SpaCy and GLiNER numbers are real. Ours are a bet.

SpaCy only covers 7 types natively. How does Presidio get to more?

Presidio stitches together three detection methods:

1. SpaCy NER handles names, organizations, locations, dates — things that need language understanding. This is the "smart" part.

2. Regex patterns handle structured PII like SSNs (\d{3}-\d{2}-\d{4}), emails (.*@.*\..*), phone numbers, IP addresses. These are brittle pattern-matching rules.

3. Validation/checksum logic handles credit cards (Luhn algorithm), IBANs (mod-97 check), etc.

This hybrid works. It's production-proven. But it has a fundamental problem: the regex recognizers and the NER model don't talk to each other. SpaCy doesn't know that the regex found an SSN two tokens later. Each detection method operates independently and their outputs are merged.

The gap: Regex can't use context. The pattern 123-45-6789 looks like an SSN, but so does a serial number, a tracking code, or a phone extension. Presidio has a "context-aware enhancer" that boosts confidence when it sees keywords like "SSN" or "social security" nearby, but it's a heuristic patch, not learned reasoning. Our CharCNN learns these patterns jointly with context in a single model.
GLiNER can detect "any" entity type. Does that mean it's automatically better?

It's more flexible, not more accurate. Zero-shot means GLiNER has never seen a training example labeled "CRYPTO_WALLET" — it tries to figure out what you mean from the type name alone. Sometimes that works well ("PERSON" is pretty clear), sometimes it doesn't ("MARITAL_STATUS" is vague).

Once you fine-tune GLiNER for PII, you've given up the zero-shot advantage — and now you're comparing a fine-tuned 460M-param model to our fine-tuned 71M-param model.

The uncomfortable truth about zero-shot: NVIDIA's GLiNER-PII is 460M parameters, fine-tuned on PII data, and gets 0.64 F1 on AI4Privacy. That's the same dataset we're training on. If a 460M-param fine-tuned model gets 0.64 on this dataset, something about the GLiNER architecture isn't ideal for PII. The likely reason: no character-level features. SSNs, credit cards, and IBANs are defined by their character patterns, and GLiNER only sees subword tokens.

Presidio got 0.29 F1 on structured PII? That seems terrible.

It is terrible, and it's instructive. That 0.29 was on the Kaggle PII detection dataset, which has diverse PII types in structured formats. Presidio's regex recognizers are designed for well-formatted PII (standard US SSN format, standard email format). When the data has non-standard formats, international phone numbers, or PII embedded in unusual contexts, the regex rules fall apart.

The 0.85 number is on "general text" that tends to have cleaner, more standard PII. In the real world, you see both.

This is the fundamental weakness of rule-based PII: Regex doesn't generalize. 123-45-6789 matches the SSN regex, but SSN 123 45 6789 or social: 123456789 might not. A learned model that understands "this looks like an SSN based on the characters AND the surrounding context" handles variation naturally.
The "custom fine-tuned transformer" in that benchmark got 0.94-0.95 F1. That's what we're trying to build, right?

Exactly. That benchmark result from the 2024 arxiv text anonymisation study confirms that a task-specific fine-tuned transformer is the best approach for PII detection — consistently beating both SpaCy/Presidio (~0.85) and zero-shot GLiNER (~0.61-0.81).

Our model adds two things on top of the standard fine-tuned transformer approach: the Character CNN (for structured PII patterns) and the CRF head (for sequence validity). Both are designed to push the number above where a plain fine-tuned DeBERTa would land.

Whether we get to 0.94+ is the open question. The architecture supports it. The training data supports it. But we need to actually train on the full dataset and measure.

Wait. So Gretel's 0.95 F1 was tested on data from the same generation pipeline as the training data?

Yes. Both the 50K training examples and the 5K test examples were generated by the same system: Gretel Navigator using Mistral-Nemo-2407, same 47 domains, same 46 entity types, same generation templates. The test set is a random held-out split from the same distribution.

This is like studying for a test using the answer key, then taking a test written by the same person. You'll score well, but it doesn't mean you understand the material.

The honest question is: what happens when Gretel's model sees real-world documents it wasn't trained on? We don't know — they haven't published cross-dataset results. But NVIDIA did publish cross-dataset results for their model, and the answer is sobering.

NVIDIA gets 0.87 on their own data but 0.64 on AI4Privacy. That's a 23-point drop. Why?

Three reasons, all of which matter for understanding what these models actually learn:

1. Different entity definitions. Nemotron-PII uses first_name and last_name as separate entity types. AI4Privacy uses FIRSTNAME, LASTNAME, FULLNAME, and NAME. If the model was trained to find first_name and the test data expects FIRSTNAME, every match is wrong even if the model found the right text span. Label normalization is essential — and it's not trivial.

2. Different synthetic generation styles. Nemotron uses Mistral-Small-24B with NeMo Data Designer. AI4Privacy uses a proprietary generation pipeline. Each LLM produces text with its own characteristic patterns — sentence structures, word choices, how it formats PII in context. A model trained on one LLM's output may not generalize to another's.

3. Different domain distributions. Nemotron covers 50+ industries with 90% unstructured text. AI4Privacy covers 229 use cases with 5 interaction styles across 4 languages. The entity frequency distributions, context patterns, and text styles are fundamentally different.

The uncomfortable implication: If the best-funded PII model (NVIDIA, 570M params, fine-tuned GLiNER-large) drops from 0.87 to 0.64 when evaluated on a different dataset, then every in-distribution score in this space is inflated. Gretel's 0.95 would likely be 0.70-0.75 on AI4Privacy. The hybrid study's 0.91 would likely drop to the 0.70s on non-financial text. Published PII F1 scores are not comparable across models unless they're measured on the same test set.
What about that "custom transformer" that got 0.95 F1 in the arxiv benchmark?

That number is real but misleading for our purposes. It was measured on CoNLL-2003, which has only 4 entity types: PERSON, LOCATION, ORGANIZATION, and MISC. The training data is ~14K sentences of Reuters newswire — real text, not synthetic.

Detecting 4 entity types in clean newswire text is a fundamentally easier task than detecting 46-81 PII types in diverse synthetic or real-world documents. A 0.95 on CoNLL-2003 doesn't tell us anything about how that model would perform on SSNs, credit cards, or medical record numbers — because those entities don't exist in CoNLL-2003.

The useful takeaway: fine-tuned transformers with CRF consistently outperform other approaches on NER. The CRF in that same benchmark scored 0.93, nearly matching the custom transformer. Our architecture includes both.

All three of our planned training datasets are synthetic. Is that a problem?

It's a risk, not a dealbreaker. Here's the breakdown of what we're working with:

The fact that each dataset was generated by a different system is actually an advantage. A model trained on three different synthetic distributions is forced to learn the underlying PII patterns rather than the quirks of one particular LLM's output style. It's a form of data augmentation.

The real risk with synthetic data: All three generators produce "clean" PII — perfectly formatted SSNs, standard email formats, well-structured addresses. Real-world PII is messy: OCR errors, inconsistent formatting, PII split across multiple lines, abbreviations, typos. Our model may train on clean patterns and struggle with noisy real-world data. This is something to test explicitly during evaluation.

Is there a standard PII benchmark everyone agrees on?

No. This is one of the biggest problems in PII detection research. Unlike NLP where everyone reports on GLUE, SuperGLUE, or SQuAD, PII detection has no universal benchmark.

Each team evaluates on their own data: Gretel on Gretel's test set, NVIDIA on Nemotron's test set, Knowledgator on E3-JSI. This makes published F1 numbers nearly impossible to compare directly. A 0.95 on one test set might be equivalent to a 0.70 on another.

What we should do: After full training, evaluate on every available test set — not just our own held-out split. Run on AI4Privacy test, Nemotron test, Gretel test, and ideally PIILO (if we can get access) and real annotated documents. Report all numbers, not just the best one. That level of transparency is rare in this space and would make our results credible.

The size difference matters more than you'd think. At 25 MB, DataFog v1 can run in a browser (via ONNX.js / WebAssembly), on a mobile device, in a serverless function with minimal cold start, or on an IoT edge device. At 741 MB (SpaCy) or 1.3 GB (GLiNER), you need a proper server with enough RAM, and cold starts become an issue for serverless.
Is 10ms per 128 tokens realistic?

For a DeBERTa-xsmall model quantized to INT8 via ONNX Runtime, yes, this is a reasonable target. DeBERTa-xsmall has 12 layers with 384-dim hidden size and 6 attention heads. After INT8 quantization:

Compare to GLiNER which must encode 50+ entity type tokens alongside the text, perform span-entity matching over all candidate spans, and run on a larger backbone (768-dim, 12 heads). The ~50-80ms estimate for GLiNER is consistent with published numbers.

SpaCy's CNN architecture is a different beast — CNNs are extremely fast on CPU, which is why it achieves ~3,000 words/sec. But it trades accuracy for that speed.

7. Architectural Tradeoffs
What can our model do that GLiNER fundamentally can't?

Three things:

1. See character patterns. GLiNER and SpaCy operate on subword tokens. They never see the raw characters. Our CharCNN looks at the actual characters of each token and can learn that "three digits, dash, two digits, dash, four digits" is an SSN pattern. GLiNER sees ["_555", "-12", "-34", "56"] and has to learn the pattern indirectly from subword token co-occurrence. This is why NVIDIA's GLiNER-PII gets only 0.64 F1 on AI4Privacy despite being 460M parameters.

2. Enforce sequence validity. Our CRF head physically cannot output I-EMAIL after B-PERSON. The transition matrix makes that transition score negative infinity. GLiNER uses span matching with greedy decoding — it can produce contradictory extractions (overlapping spans with different types) and has no mechanism to enforce sequential BIO constraints.

3. Run without entity type tokens in the input. GLiNER prepends entity type names as tokens, which means: (a) the effective sequence gets longer, (b) with 50+ types, you're adding 50+ tokens to every input, and (c) performance degrades beyond ~30 types because the entity type tokens compete with the actual text for attention. Our model always predicts over all 81 types simultaneously with zero additional input overhead.

What can GLiNER do that our model fundamentally can't?

One critical thing: detect entity types it has never been trained on.

If a customer says "we also need to detect EMPLOYEE_BADGE_NUMBER and INTERNAL_PROJECT_CODE," GLiNER can try to find those right now, zero-shot, with no changes. We would need to: (1) collect labeled examples of those types, (2) add them to the label schema, (3) retrain or fine-tune, (4) redeploy. That's days or weeks of work vs. minutes.

For a PII product, the question is: how often do entity types actually change? If the taxonomy is stable (SSNs, credit cards, names, emails), the zero-shot flexibility isn't worth the accuracy and speed cost. If customers regularly need custom entity types, it's a significant advantage.

The pragmatic answer: PII taxonomies are relatively stable. GDPR, CCPA, and HIPAA define the categories. New PII types emerge slowly (crypto wallets, biometric data), not weekly. A quarterly retraining cycle can handle taxonomy changes. The speed and accuracy gains from a specialist model outweigh the flexibility cost for this domain.
What can SpaCy/Presidio do that neither of the other two can?

Validation and checksums. Presidio doesn't just detect credit card numbers — it validates them with the Luhn algorithm. It checks IBAN checksums. It validates SSN format rules (not starting with 000, etc.). Neither GLiNER nor our model does this natively. They predict "this is a credit card number" but don't verify it's a valid one.

This matters for precision. A learned model might predict that 1234-5678-9012-3456 is a credit card, but Luhn would tell you it's not a valid card number — it's probably a serial number or tracking code.

Not mutually exclusive. In production, you'd likely combine our model's predictions with Presidio-style validation as a post-processing step. Use the model for detection, then validate structured PII with checksums. Best of both worlds.
8. The Honest Case Against Building Our Own
What are the strongest arguments for NOT building this model?

Let's be honest about the risks:

1. It might not beat the fine-tuned GLiNER variants.
Gretel's fine-tuned GLiNER-bi-base achieves 0.95 F1 on their PII test set. That's already excellent. If our model lands at 0.92, we've spent weeks building something marginally worse than an off-the-shelf model. The CharCNN and CRF should help, but "should" and "does" are different things.
2. DeBERTa-v3-xsmall might be too small.
384-dim hidden size vs GLiNER's 768-dim. We're betting the CharCNN and CRF compensate for the smaller backbone. If contextual PII types (PERSON, LOCATION, ORGANIZATION) underperform, the backbone is the bottleneck and we'd need to upgrade to DeBERTa-v3-base, which doubles the model size and partially erases our efficiency advantage.
3. Maintenance burden.
SpaCy and GLiNER are maintained by dedicated teams (Explosion AI, Fastino AI). They get regular updates, bug fixes, and community contributions. Our model is something we maintain ourselves. Every backbone security patch, every PyTorch version upgrade, every new entity type — that's on us.
4. The 0.85 Presidio number might be "good enough."
For many PII use cases, 85% F1 with fast CPU inference and regex validation is perfectly acceptable. The incremental value of going from 0.85 to 0.93 depends on the customer's tolerance for missed PII. If false negatives aren't catastrophic for the use case, Presidio is the safer choice.
5. Training data quality is unvalidated.
We're planning to train on AI4Privacy + Nemotron-PII + Gretel. These datasets have different annotation conventions, different entity type definitions, and potentially conflicting labels. Label noise in training data can silently cap model performance. We haven't audited the label quality yet.
9. The Case For Building Our Own
Given all those risks, why is this still worth doing?

Four reasons that address different concerns:

1. The evidence says task-specific fine-tuned models win.
Across every benchmark I've found, a fine-tuned transformer trained on PII data outperforms both SpaCy/Presidio and zero-shot GLiNER. The 2024 arxiv text anonymisation benchmark: custom transformer 0.94-0.95 vs Presidio 0.85. The 2025 Scientific Reports hybrid study: 0.91. The literature is clear: if you have the data and the task is well-defined, a specialist beats a generalist. We have 360K labeled examples. PII detection is well-defined.
2. No existing model has character-level features + CRF + transformer for PII.
This is the gap identified in the research survey. Piiranha uses a transformer but no character features (280M params). GLiNER uses a transformer with span matching but no character features. Presidio uses regex for characters but no learned features. Our architecture is the first to combine all three in a PII-specific model. This is a genuine architectural contribution, not just a different fine-tuning job.
3. The deployment profile is unique.
25 MB, CPU-only, 10ms latency, no GPU. No existing PII model hits this profile. This unlocks use cases that SpaCy and GLiNER can't serve: browser-based PII scanning, mobile device deployment, serverless functions with tight cold-start budgets, edge devices in healthcare/finance. For DataFog as a product, this deployment flexibility is a competitive moat.
4. We own the model and the training pipeline.
Depending on Presidio or a Gretel/NVIDIA model means depending on their roadmap, their licensing decisions, and their definition of "PII." Owning the model means we can add entity types, adjust tier thresholds, retrain on domain-specific data, and ship updates on our own schedule. For a PII product company, this control is strategically important.

10. What We Need to Prove
What are the key experiments that will confirm or kill this approach?

In priority order, these are the experiments that resolve the biggest unknowns:

#ExperimentWhat It ProvesKill Criterion
1 Full training on 360K examples, eval on held-out test set Whether the architecture generalizes beyond memorization If F1 < 0.85 on test set, something is fundamentally wrong
2 CharCNN ablation: Train with and without CharCNN, compare Whether character features actually help or are dead weight If CharCNN adds < 0.3 F1 on structured PII types, it's not worth the complexity
3 Backbone size ablation: Train with DeBERTa-xsmall vs base Whether 384-dim is the bottleneck If base adds > 2 F1 points, we should probably use base
4 Head-to-head benchmark vs GLiNER-PII on AI4Privacy test split Whether we actually beat the competition on the same data If we lose to GLiNER-PII despite being purpose-built, rethink the approach
5 ONNX INT8 export and latency measurement Whether the 10ms target is achievable with CRF decode If latency > 30ms, the speed advantage over GLiNER is modest, not transformative
The smoke test was experiment 0. It answered: "Is the model wired correctly? Can the architecture learn PII at all?" Answer: yes (F1 0.992 on overfit). The experiments above answer the harder questions about generalization, component value, and competitive positioning. Full training is next.
