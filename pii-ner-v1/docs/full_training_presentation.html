From Smoke Test to Full Training

The smoke test validated model wiring on 100 AI4Privacy examples. Going to 360K requires solving three new problems.

1 Data Heterogeneity

3 datasets use different formats. AI4Privacy has pre-tokenized tokens+tags. Nemotron and Gretel use raw text + character-offset spans.

2 Label Normalization

100+ source label names must map to 44 canonical entity types. "FIRSTNAME", "FIRST_NAME", "first_name", "PER" → all become PERSON.

3 Optimizer Lifecycle

Custom optimizer + HuggingFace Accelerate + mixed precision = gradient scaler crash. Needed architectural fix, not a config flag.

The smoke test is necessary but not sufficient. It tests model wiring. Full training tests data engineering, numerical stability at scale, and generalization.

The Format Problem: Tokens vs Spans

The smoke test only used AI4Privacy (token format). Nemotron and Gretel use a fundamentally different representation.

Token-Based (AI4Privacy)

{ "tokens": ["John", "Smith", "lives", "at", "123", "Main", "St"], "ner_tags": ["B-PERSON", "I-PERSON", "O", "O", "B-STREET_ADDRESS", "I-STREET_ADDRESS", "I-STREET_ADDRESS"] }

Already tokenized at word level. Tags align 1:1 with tokens. Direct input to _tokenize_and_align().

Span-Based (Nemotron, Gretel)

{ "text": "John Smith lives at 123 Main St", "spans": [ {"start": 0, "end": 10, "label": "PERSON"}, {"start": 20, "end": 31, "label": "ADDRESS"} ] }

Raw text + character offsets. Must be whitespace-tokenized, then spans must be projected onto word boundaries to produce BIO tags.

This was a blocking issue. The original load_single_dataset() only supported token format. Nemotron and Gretel failed with ValueError: Cannot find token column. Both datasets loaded 0 examples in the initial attempt.

Span-to-BIO Conversion

The _spans_to_bio() function converts character-offset spans to word-level BIO tags in four steps.

1 Whitespace Tokenize

text = "John Smith lives at 123 Main St" tokens = ["John", "Smith", "lives", "at", "123", "Main", "St"] offsets = [(0,4), (5,10), (11,16), (17,19), (20,23), (24,28), (29,31)]

Regex \S+ with finditer() captures both token text and character positions.

2 Parse & Validate Spans

spans = ast.literal_eval(spans_str) # Filter invalid, map labels, sort by start offset valid = [(0, 10, "PERSON"), (20, 31, "STREET_ADDRESS")]

Spans may be strings or lists. Invalid/unmapped labels are silently dropped to O.

3 Project Spans onto Tokens

for each token (tok_start, tok_end): if tok_start ≥ span_start and tok_start < span_end: if first_token_of_span: tag = "B-{label}" else: tag = "I-{label}"

Linear scan with span pointer advancement. O(n+m) where n=tokens, m=spans.

4 Feed to Existing Pipeline

tokens, bio_tags = _spans_to_bio(text, spans, dataset_name) # Same downstream as token format: return _tokenize_and_align(tokens, bio_tags, tokenizer)

Both formats converge to (tokens, bio_tags) → subword alignment.

The 4-Tier PII Taxonomy

44 entity types organized by sensitivity. Each tier has a different recall target — miss tolerance decreases with severity.

Tier 1: Critical — Target ≥ 0.98 Recall

SSN, Credit Card, Bank Account, Passport, Drivers License, Tax ID

Direct identifiers. A single miss = potential breach. Zero tolerance in production.

Tier 2: High Sensitivity — Target ≥ 0.95 Recall

Person, Email, Phone, DOB, Street Address, IP Address

Strong identifiers. Can uniquely identify individuals alone or in combination.

Tier 3: Moderate — Target ≥ 0.90 Recall

Username, Date, Location, Organization, URL, License Plate, Age, Nationality, Gender, Ethnicity, Religion, Marital Status

Contextual PII. Identifying in combination. Higher ambiguity (dates can be non-PII).

Tier 4: Domain-Specific — Target ≥ 0.85 Recall

Medical Record, Employee ID, IBAN, SWIFT, PIN, Password, Biometric, Crypto Wallet, Insurance Number, Salary, and 11 more

Rare in general text. Lower recall target reflects expected data scarcity, not reduced importance.

Design choice: Tier 4 has a lower target, not a lower priority. With 360K examples, many Tier 4 types may have only hundreds of instances. The 0.85 target acknowledges the data scarcity constraint.

The Gradient Scaler Bug

A two-layer debugging story: the obvious fix failed, the real fix required understanding Accelerate internals.

Attempt 1: Switch to BF16

ValueError: Attempting to unscale FP16 gradients. # Hypothesis: FP16 GradScaler clashes with CRF # Fix: Switch to bf16=True (A100 native, no scaler) training_args = TrainingArguments( fp16=False, bf16=True, # A100 supports bf16 natively ... )

Result: Same crash. BF16 shouldn't use a gradient scaler at all. Why was it still firing?

Root Cause: Accelerate Optimizer Bypass

# The real problem: trainer = PiiTrainer( ... optimizers=(custom_optimizer, None), # <-- THIS ) # When you pass optimizers=(), Accelerate skips # its normal optimizer wrapping lifecycle: # # Normal: Trainer.create_optimizer() # → Accelerate.prepare(optimizer) # → Wraps optimizer for mixed precision # # Bypassed: raw optimizer goes straight to # training loop → gradient scaler sees raw # FP16 params → crash
Key insight: The bug wasn't about FP16 vs BF16. It was about who owns the optimizer. Passing optimizers=(optimizer, None) bypasses Accelerate's prepare() call, which handles gradient scaler integration. The fix is to let the Trainer create the optimizer via its normal lifecycle.

The Fix: create_optimizer() Override

Instead of passing a custom optimizer from outside, we override the Trainer's optimizer creation hook.

Before (Broken)

# External optimizer bypasses Accelerate backbone = [p for n, p in model.named_parameters() if "deberta" in n] head = [p for n, p in model.named_parameters() if "deberta" not in n] optimizer = AdamW([ {"params": backbone, "lr": 2e-5}, {"params": head, "lr": 1e-3}, ]) trainer = PiiTrainer( ..., optimizers=(optimizer, None), ## BUG )

After (Fixed)

# PiiTrainer creates optimizer internally class PiiTrainer(Trainer): def __init__(self, *args, lr_backbone=None, lr_head=None, **kwargs): self.lr_backbone = lr_backbone self.lr_head = lr_head super().__init__(*args, **kwargs) def create_optimizer(self): backbone = [p for n, p in self.model.named_parameters() if "deberta" in n and p.requires_grad] head = [p for n, p in self.model.named_parameters() if "deberta" not in n and p.requires_grad] self.optimizer = AdamW([ {"params": backbone, "lr": self.lr_backbone}, {"params": head, "lr": self.lr_head}, ], weight_decay=self.args.weight_decay) return self.optimizer
Why this works: create_optimizer() is called by Trainer.train() after Accelerate.prepare() has set up the training context. The optimizer is properly wrapped for mixed precision before the first forward pass.

Mixed Precision + CRF: A Delicate Balance

The CRF head computes log-sum-exp over 89×89 transition matrices. This is numerically unstable in half precision.

The Three-Layer Defense

Layer 1: Force FP32 before CRF

fused = fused.float() # Cast to FP32

Ensures CRF input is FP32 regardless of autocast state.

Layer 2: Disable autocast in CRF

with torch.amp.autocast( device_type=fused.device.type, enabled=False): crf_output = self.crf_head(...)

Prevents autocast from recasting nn.Linear weights back to FP16 inside the CRF.

Layer 3: BF16 on capable hardware

BF16 has the same exponent range as FP32 (8 bits), avoiding overflow in log-sum-exp. No gradient scaler needed.

Precision Comparison

FormatExponentMantissaRangeScaler?
FP328 bits23 bits~3.4×1038No
BF168 bits7 bits~3.4×1038No
FP165 bits10 bits~6.5×104Yes
FP16 CRF failure mode: Transition scores for 89 labels can exceed FP16 range (65504) in the log-sum-exp computation, producing inf → NaN loss.

GPU Auto-Detection

gpu_mem = torch.cuda.get_device_properties(0).total_memory if gpu_mem / 1e9 >= 20: # A100, H100 bf16=True, fp16=False else: # T4, V100 bf16=False, fp16=True # FP32 CRF is the safety net

Why These Choices

  • 50x LR ratio: Validated in smoke test — DeBERTa representations must be preserved while CRF transitions (89×89 matrix) need aggressive learning
  • 10 epochs: With 360K examples and effective batch 32, each epoch is ~11,250 steps. 10 epochs = ~112K steps — well within the typical fine-tuning budget
  • 256 seq len: Covers 95%+ of PII-containing text. Longer sequences have diminishing returns and quadratic attention cost
  • Linear schedule: Standard for NER fine-tuning. Cosine provides marginal benefit for <20 epoch runs
  • save_total_limit=3: Keeps 3 best checkpoints. With ~5GB per checkpoint, this prevents disk exhaustion on Colab

Pre-Flight Validation: Test Without Data

Downloading and processing 360K examples takes 10-15 minutes. We added a synthetic data validation step to catch pipeline bugs before that investment.

The Validation Cell

What It Tests

  • Optimizer creation: create_optimizer() runs with differential LRs
  • Mixed precision: Accelerate wraps the optimizer correctly for bf16/fp16
  • Forward pass: CRF loss computation doesn't produce NaN
  • Backward pass: Gradient scaler doesn't crash on unscaling
  • 3 full steps: Enough to exercise the entire training loop including gradient accumulation
This caught the gradient scaler bug that previously only surfaced 15 minutes into training (after data download + processing). Saves ~$1 of A100 time per failed attempt.

Key decisions and their rationale, for the paper's methodology section.

FAQ: Data Engineering

Q: Why whitespace tokenization for spans instead of spaCy or stanza?
Span annotations use character offsets into the raw text. Whitespace tokenization with regex \S+ preserves exact character positions. spaCy's tokenizer splits punctuation and contractions differently, which can misalign character offsets. We need alignment, not linguistic quality.
Q: What happens when a span boundary falls mid-word?
The overlap check uses tok_start ≥ span_start and tok_start < span_end. If a span starts mid-word, the entire word gets the B- tag (conservative: over-tags rather than under-tags). This is rare in practice since span annotators typically respect word boundaries.
Q: Why ast.literal_eval() instead of json.loads()?
Gretel's span column stores Python list-of-dict representations with single quotes: [{'start': 0, 'end': 5, ...}]. json.loads() requires double quotes and would fail. ast.literal_eval() handles both formats safely.
Q: Why not use the datasets' native label IDs?
Each dataset has its own label vocabulary with different ordering and granularity. AI4Privacy uses 40+ labels, Nemotron uses 30+, Gretel uses 25+. We need a single consistent ID space across all datasets. The canonical mapping also lets us decide semantic granularity (e.g., CITY and STATE both map to LOCATION).
Q: How are unmapped labels handled?
map_label() returns None for unrecognized labels, which _normalize_tags() converts to "O". This means rare or dataset-specific labels (e.g., BUILDING_NUMBER) are treated as non-entities rather than crashing. We log unmapped labels for auditing.
Q: Why 80/10/10 split instead of fixed test set?
No established PII NER benchmark exists (unlike CoNLL-03 for general NER). We create our own held-out test set from the combined data. 10% of 360K = ~36K test examples — large enough for stable per-entity-type metrics.

FAQ: Optimizer & Training

Q: Why not use optimizers=() and just be careful with Accelerate?
The Accelerate integration is an implementation detail of HuggingFace Trainer that can change between versions. create_optimizer() is the documented hook for custom optimizers. Using the public API means our code survives Trainer/Accelerate upgrades without silent breakage.
Q: Why AdamW and not AdaFactor or LAMB?
AdamW is the standard optimizer for transformer fine-tuning. AdaFactor saves memory (no second moment) but can be unstable with small batch sizes. LAMB is designed for large-batch training (≥4K). With effective batch size 32, AdamW is the safe choice.
Q: Why 50x LR ratio specifically?
Derived empirically from the smoke test. Standard NER fine-tuning uses 2e-5–5e-5 for the backbone. The CRF head starts from random initialization with an 89×89 transition matrix — it needs aggressive learning. 1e-3 is a standard "train from scratch" LR. The 50x ratio ensures the backbone is gently tuned while the head learns fast.
Q: The CRF forces FP32 computation. Doesn't this negate the speed benefit of mixed precision?
The CRF head is ~438K params out of 71.1M total (<1%). DeBERTa's self-attention and feed-forward layers (99% of compute) still run in BF16. The FP32 CRF adds negligible overhead. Benchmarks show <3% wall-clock difference vs all-BF16 (if it didn't crash).
Q: Why remove_unused_columns=False?
HuggingFace Trainer automatically removes dataset columns that aren't in the model's forward() signature. Our model expects char_ids, which isn't a standard transformer input. Without this flag, char_ids gets silently dropped and the CharCNN receives no input.
Q: Why not learning rate warmup steps instead of warmup ratio?
Warmup ratio (0.1 = 10% of total steps) is dataset-size agnostic. The same config works for 100 examples (smoke test) and 360K (full training) without recalculation. Note: recent Transformers versions show a deprecation warning for warmup_ratio in favor of warmup_steps — both work equivalently.

FAQ: Model Architecture

Q: Why DeBERTa-v3-xsmall instead of -small or -base?
The xsmall variant (70.7M params, 384 hidden dim) is the best tradeoff for serving PII detection at scale. At inference, this model will process millions of documents. The -base variant (86M, 768 hidden) is 2× slower with only marginal F1 improvement on NER benchmarks. We can always distill a -base model down later.
Q: How does the gating fusion work?
For each token position, a learned gate g = σ(W[char; context] + b) produces a scalar in [0,1]. The fused representation is g · char + (1-g) · context. The gate learns to trust character features for format-heavy entities (SSN, credit card) and context features for semantic entities (person names, organizations).
Q: What are the CharCNN filter widths (3,4,5) capturing?
Width-3: digit trigrams (123), punctuation patterns (X-X). Width-4: common prefixes/suffixes, year patterns (2024). Width-5: format signatures (XXX-XX = SSN prefix, ###-## = ZIP). The multi-width design lets the model learn patterns at different character scales simultaneously.
Q: Why CRF instead of constrained decoding?
Constrained decoding (e.g., masking invalid transitions at inference) prevents illegal sequences but doesn't learn transition preferences. The CRF learns that B-PERSON → I-PERSON is much more likely than B-PERSON → I-EMAIL. This soft constraint improves boundary detection even when emission scores are ambiguous.
Q: Is the CRF transition matrix large enough to matter?
The transition matrix is 89×89 = 7,921 parameters. This is tiny compared to the model's 71M total. Many transitions are effectively zero (B-SSN → I-PERSON never happens), so the matrix is very sparse in practice. The Viterbi decode is O(T×K²) where T=seq_len, K=89 — still fast at ~2ms per sequence.
Q: What's the prediction_step override doing?
The standard Trainer expects logits from the model and applies argmax. Our model returns CRF-decoded predictions (Viterbi best path), which are already discrete label IDs. The override extracts output.predictions directly instead of applying argmax to logits.
